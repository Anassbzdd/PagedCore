## Controlled T4 comparisons

All controls use the pinned weights, eager HF, FP16 inputs/storage and the
existing deterministic reference math settings. They replay reference-selected
tokens for three decode steps at prompt lengths 15 (single) and
1/15/16/17/49 (mixed). Rows reverse order between steps.
The table reports the largest observed `abs(actual-reference) /
(tolerance + tolerance * abs(reference))`; values above one fail the contract.

| Diagnostic path | Batch | Maximum logit ratio | Maximum K/V ratio |
|---|---:|---:|---:|
| Original paged attention | 1 | 2.2488 | 2.1805 |
| Original paged attention | 5 | 5.0729 | 4.4859 |
| Dense-attention control in the same staged decoder | 1 | 0 | 0 |
| Dense-attention control in the same staged decoder | 5 | 5.1984 | 4.2658 |
| Dense control plus independent-row `bmm` projections/MLP | 5 | 4.1810 | 3.8875 |

The dense control reconstructs history **only as a diagnostic**, outside the
serving implementation. It is prohibited as a production fix. Its exact
single-request result isolates attention arithmetic as sufficient to explain
that case's drift. Its mixed-batch failure also isolates a batch-dependent
numerical difference outside paged attention. Replacing matrix products with
independent-row `bmm` does not remove that difference.

Score-rounding, probability-rounding, per-head/grouped score products,
reciprocal normalization and one-page eager experiments did not produce a
passing replacement. Eager FP16 attention rounds score products and normalized
probabilities; the implemented online primitive retains FP32 scores and running
weighted values. Component controls observe small attention differences that
accumulate through the decoder. PyTorch also documents that
[batched and separate computations can differ numerically](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html#batched-computations-or-slice-computations).

All diagnostic next-token argmax comparisons matched, including all 18
row/step comparisons of the original implementation. This does not establish
complete greedy generation, EOS handling, the 256-token path, or acceptable
tensor/logit parity. It does not exclude additional bugs outside these cases.

## Remaining decision and work

No engine arithmetic or tolerance was changed during this investigation.
The existing no-full-history, FP32 online-attention and eager-reference
requirements must be reconciled before a numerical redesign or separately
measured policy can be accepted. Keep the current gate open; do not relabel
these failures as passes. Any implementation change needs regression coverage
and a new clean, attributable T4 run. Maximum-active workspace and CUDA page
reuse ordering remain separate P5.7 requirements.
